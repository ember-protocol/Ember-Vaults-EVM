# EVM contracts: agent guide

Orientation layer for the EVM contracts in this tree. Depth lives in the sibling docs listed below; this file routes you to them, maps the Solidity files, pins down ERC-4626 conformance, and records what the code enforces that no sibling doc states. Line references are `contracts/File.sol:line` against the current tree. The Sui (`sui/`) and Solana (`solana/`) implementations of the same protocol are separate chains with their own docs; nothing here applies to them.

## ERC-4626 conformance and where it ends

`EmberVault` and `EmberETHVault` inherit OZ `ERC4626Upgradeable` (`contracts/EmberVault.sol:54`, `contracts/EmberETHVault.sol:65`); `AtomicLiquidity` does not inherit it and only mimics the view names (`asset`, `totalAssets`, `convertToShares`, `convertToAssets`, `maxDeposit`, `balanceOf`, `totalSupply`) on non-transferable book-entry shares (`contracts/AtomicLiquidity.sol:1876-1928`).

Implemented with the standard's exact signatures on both ERC-4626 vaults: `asset()`, `totalAssets()`, `convertToShares(uint256)`, `convertToAssets(uint256)`, `maxDeposit(address)`, `maxMint(address)`, `maxWithdraw(address)`, `maxRedeem(address)`, `previewDeposit`, `previewMint`, `previewWithdraw`, `previewRedeem`, `deposit(uint256,address)`, `mint(uint256,address)`, `withdraw(uint256,address,address)`, `redeem(uint256,address,address)`, plus ERC-20. The overrides are:

- `totalAssets()` returns `convertToAssets(totalSupply())`, never a balance (`contracts/EmberVault.sol:1474-1482`).
- `_convertToShares` ignores its `Math.Rounding` argument and always floors `assets * rate / 1e18` (`contracts/EmberVault.sol:1492-1503`). Consequently `previewWithdraw`, which OZ routes through `_convertToShares` with ceiling, floors here. `_convertToAssets` ceils only when asked (`mint`/`previewMint`), floors otherwise (`contracts/EmberVault.sol:1513-1531`).
- `withdraw` and `redeem` unconditionally revert `UseRedeemShares()` (`contracts/EmberVault.sol:1537-1547`, `contracts/EmberETHVault.sol:1867-1876`), yet `maxWithdraw`/`maxRedeem` return the holder's full balance (`contracts/EmberVault.sol:1556-1574`). The standard requires `maxWithdraw`/`maxRedeem` to return 0 when the operation is disabled; integrators that gate on `max*` will call a function that always reverts.
- `maxDeposit`/`maxMint` return 0 under vault or protocol pause and otherwise the `maxTVL` headroom (`contracts/EmberVault.sol:1580-1606`); `deposit`/`mint` additionally revert for blacklisted or sub-account depositors/receivers, validator allow-list misses, and parking-lot gating (`contracts/EmberVault.sol:1821-1849`), none of which `max*` reflects.
- Extensions outside the standard: `depositWithPermit`, `mintWithPermit`, `redeemShares`, `cancelPendingWithdrawalRequest`, `bridgeMint`/`bridgeBurn`; on the ETH vault `depositETH`, `mintWithETH`, `claimWithdrawal*`, `recoverUnclaimedWithdrawal`.

Slippage: `deposit(uint256 assets, address receiver)` and `mint(uint256 shares, address receiver)` carry the standard's fixed signatures, so a depositor cannot pass a minimum-shares or maximum-assets bound, and the code adds none (`contracts/EmberVault.sol:1615-1692`). Nothing substitutes for it on the user side. What bounds the exposure is that the conversion depends only on `rate.value`: it changes solely through `updateVaultRate`, which the rate manager may call at most once per `rateUpdateInterval` (protocol floor one hour, `contracts/EmberProtocolConfig.sol:34`) and by at most `maxRateChangePerUpdate` relative to the old value (`contracts/EmberVault.sol:908-918`; deploy default 1 percent per `scripts/deploy/README.md`). Fee accrual before a deposit does not touch the rate (`contracts/EmberVault.sol:1749-1813`). So between a `previewDeposit` and the mined `deposit` the shares can move only if a rate update lands in between, and then by at most that bound; `test/foundry/EmberVaultFuzz.t.sol:288-302` asserts `previewDeposit == deposit` in the same state. The only user-supplied slippage floor in this tree is `minNetOut` on `AtomicLiquidity.swapEmberShares` (`contracts/AtomicLiquidity.sol:1537-1542`, enforced at `contracts/libraries/AtomicLiquidityLib.sol:524`); the OFT adapter's `minAmountLD` guards dust removal, not price (`contracts/EmberVaultMintBurnOFTAdapter.sol:418-429`).

Asynchronous withdrawal: exit is request-then-settle. `redeemShares(shares, receiver)` moves the shares into the vault's own balance via `_spendAllowance` + `_transfer` (so the caller must first `approve(vault, shares)` on the vault token, `contracts/EmberVault.sol:1196-1197`; see `test/RedeemShares.test.ts:130`), records `estimatedWithdrawAmount`, and appends to `pendingWithdrawals`. The operator's `processWithdrawalRequests(n)` burns and pays at the rate current at processing time, recomputing the amount and ignoring the stored estimate (`contracts/EmberVault.sol:2072`). This is not ERC-7540: there is no `requestRedeem`/`pendingRedeemRequest`/`claimableRedeemRequest`, no request id returned to the user, no operator-approval model, and no user-initiated claim step; settlement is pushed by the operator, and `redeem()` never becomes callable. The NatSpec at `contracts/EmberVault.sol:45-46` and `:1551` says `requestRedeem`; the function is `redeemShares`. The ETH vault adds a pull step only on failure: an undeliverable ETH payout is escrowed in `unclaimedWithdrawals` and claimed via `claimWithdrawal`/`claimWithdrawalFor`/`claimWithdrawalTo` (`contracts/EmberETHVault.sol:1473-1530`).

## Gaps the existing docs leave

Rate direction and bounds. `rate` is shares per asset, 1e18-scaled: a higher rate mints more shares per asset, so share value falls as the rate rises (`test/fuzz/EmberVaultConversions.t.sol:145-162`). Protocol bounds are `MIN_RATE = 0.25e18`, `MAX_RATE = 5e18`, `DEFAULT_RATE = 1e18` (`contracts/EmberProtocolConfig.sol:31-33`); every vault starts at the protocol default, there is no per-vault initial rate (`contracts/EmberVault.sol:596`). `maxRateChangePerUpdate` is relative, `|new - old| / old` (`contracts/EmberVault.sol:915`).

Time units. Vault timestamps, `rateUpdateInterval`, `lastChargedAt`, validator clocks, and `timeBasedFeeThreshold` are milliseconds (`block.timestamp * 1000`, `contracts/EmberVault.sol:1726-1728`). Inside `AtomicLiquidityLib` the swap-capacity epoch and `HoldbackEntry.createdAt` use seconds (`contracts/libraries/AtomicLiquidityLib.sol:1272-1276`, `:534`).

Fee model. `platformFeePercentage` is 1e18 = 100 percent per year, capped at `MAX_FEE_PERCENTAGE = 0.1e18` (`contracts/EmberProtocolConfig.sol:36`); accrual is `netTVL * pct * elapsedMs / FEE_DENOMINATOR` on `totalAssets() - accrued` (`contracts/EmberVault.sol:1778-1796`). Accrued fees are not subtracted from `totalAssets()` or from the rate; they are an additional claim on the token balance paid by `collectPlatformFee` (`contracts/EmberVault.sol:955-966`). Every TVL-mutating path charges first (`_deposit`, `_mintShares`, `bridgeMint`, `bridgeBurn`, `processWithdrawalRequests`, `updateVaultRate`, `setFeePercentage`).

Rounding and dust. Deposits floor shares, mints ceil assets, redemptions floor assets; the remainder stays in the vault. A request whose payout floors to 0 is skipped and its shares returned, not burned (`contracts/EmberVault.sol:2102-2118`). Shares parked for redemption sit at `balanceOf(address(this))`, stay in `totalSupply()`, and therefore in `totalAssets()` and the fee base until burned.

`maxTVL` is enforced only after `deposit`/`mint` (`contracts/EmberVault.sol:1890-1891`, `:1954`). `bridgeMint` does not check it (`contracts/EmberVault.sol:1091-1108`), nor does a rate decrease that raises `totalAssets()`; `updateVaultMaxTVL` refuses a value below current TVL (`contracts/EmberProtocolConfig.sol:249-250`).

Reentrancy and trusted calls. Every state-changing external on the vaults, config, validator, and parking lot is `nonReentrant`; the OFT adapter has no guard and relies on the vault's. External calls the vaults treat as trusted: `protocolConfig` reads, `vaultValidator` (`validateDeposit`, `recordDeposit`, `calculateWithdrawalFees`), the asset token (SafeERC20; `permit` on the permit paths), WETH `deposit`/`withdraw` on the ETH vault, the strategy and whitelisted source vaults on AtomicLiquidity. Untrusted and handled by escrow rather than revert: ETH receivers (`contracts/EmberETHVault.sol:1594-1598`), holdback recipients, parking-lot refund targets (`contracts/EmberDepositParkingLot.sol:627-639`). Fee-on-transfer collateral is unsupported: `_deposit` mints against the argument, not a balance delta (`contracts/EmberVault.sol:1877-1880`); only the parking lot measures and rejects it (`contracts/EmberDepositParkingLot.sol:411-415`).

Decimals. Neither ERC-4626 vault overrides `decimals()`; shares are minted as `assets * rate / 1e18`, so at rate 1e18 one share unit equals one asset base unit. The OFT adapter requires the receipt token's `decimals() >= 6` and bridges in 6 shared decimals, burning only the dust-removed amount so the remainder stays with the sender (`contracts/EmberVaultMintBurnOFTAdapter.sol:116-118`, `:382-392`, `:434-436`).

Storage layout. OZ bases use ERC-7201 namespaces, so each contract's own variables start at slot 0 (`.openzeppelin/mainnet.json` layouts: `_vaultName` at slot 0 for both vaults). Gaps: `EmberVault` and `EmberETHVault` `uint256[48]`, `AtomicLiquidity` `[39]`, `EmberDepositParkingLot` `[40]`, `EmberProtocolConfig` `[49]`, `EmberVaultValidator` `[43]`. The convention used throughout is append the new variable immediately before `__gap` and shrink the gap by one (`contracts/EmberVault.sol:211-217`, `contracts/EmberETHVault.sol:1986-1999`); in `EmberETHVault` the two newest variables are declared after the functions, which is still the end of the layout. Structs owned by libraries (`VaultPlatformFeeLib.PlatformFee`, `WithdrawalQueueLib.Account`, `AtomicLiquidityLib.EmberShareConfig`/`HoldbackEntry`) are part of the linking vault's layout. Library addresses are baked into implementation bytecode; `getContractFactory` needs `libraries`, and deploy/validate pass `unsafeAllowLinkedLibraries: true` (`scripts/ci/validate-upgrades.ts:80-112`). `.openzeppelin/<network>.json` is committed and must be updated with every upgrade; `yarn ops:force-import` reconciles a drifted manifest.

Settlement batch bounds. `processWithdrawalRequests(n)` clamps `n` to the queue length, pops FIFO, and reverts the entire batch if any non-skipped request finds `balanceOf(vault) < withdrawAmount` (`contracts/EmberVault.sol:1372-1376`, `:2141`); nothing else bounds `n` but gas. Skips (blacklisted owner or receiver, cancelled, zero payout) return shares and advance the head. The queue array is deleted when fully drained (`:1408-1415`). Cancellation only marks the sequence number; the shares come back when the operator reaches the request (`:1278-1279`, `:2117-2118`). `EmberETHVault.getWithdrawalRequest(index)` indexes the raw array including processed (zeroed) slots (`contracts/EmberETHVault.sol:1899-1902`); `EmberVault.getPendingWithdrawal` offsets by the head (`contracts/EmberVault.sol:1434-1439`). Parking lot: `processDeposits(n)` counts slots including cancelled ones; `processDepositsUpTo(seq)` bounds by request id (`contracts/EmberDepositParkingLot.sol:507-536`).

Validator semantics. `recordDeposit` keys the anti-JIT clock by `msg.sender`, not receiver (`contracts/EmberVaultValidator.sol:154-157`); a holder with no recorded clock (transfer or bridge recipient) pays the time-based fee until fee-exempted (`:237-243`). Parking-lot forwards fix attribution through `recordDepositFor` (`contracts/EmberDepositParkingLot.sol:594-597`). Allow-list and exemption setters are operator-gated; fee percentage/threshold setters are admin-gated (`contracts/EmberVaultValidator.sol:257`, `:299`), with permanent + time-based capped at 50 percent combined (`contracts/EmberProtocolConfig.sol:519-520`).

Fuzz-asserted, prose-silent. `previewDeposit(x) == deposit(x)` (`test/foundry/EmberVaultFuzz.t.sol:288-302`); deposits above `maxDeposit` revert and otherwise keep `totalAssets() <= maxTVL` (`:205-227`); strict monotonicity of both conversions (`:234-253`).

## Build, test, verify

Hardhat owns compilation, unit tests, coverage, deployment, upgrades, and verification; Foundry exists only for fuzz tests; Echidna is configured but not wired into anything that runs. Both compile with solc 0.8.22 and `viaIR`, but Hardhat uses `optimizer.runs = 100` and Foundry `optimizer_runs = 200` with `evm_version = "paris"` (`hardhat.config.ts:13-21`, `foundry.toml:8-15`), so bytecode and sizes differ by toolchain; deployed artifacts come from Hardhat.

```bash
yarn install                               # Node >= 20, yarn 4 (packageManager in package.json)
yarn compile                               # hardhat compile -> artifacts/, typechain-types/
yarn test --network hardhat                # all Mocha/Chai tests in test/*.test.ts
yarn test test/RedeemShares.test.ts --network hardhat   # one file
yarn coverage                              # what CI runs (DEPLOY_ON=hardhat); skips contracts/testing/
yarn typecheck                             # tsc --noEmit; needs typechain-types from yarn compile
yarn format:check                          # prettier incl. prettier-plugin-solidity; CI-gated
yarn size                                  # clean + compile + EIP-170 report (hardhat net allows unlimited size)
yarn audit:setup && yarn audit:slither     # python venv + slither, SOLC_VERSION=0.8.22
yarn ci:validate-upgrades --network mainnet   # upgrades.validateUpgrade for every proxy in deployments/mainnet-deployment.json
```

`defaultNetwork` is `process.env.DEPLOY_ON` (`hardhat.config.ts:122`); with a `.env` copied from `.env.example` that is `sepolia`, so pass `--network hardhat` or export `DEPLOY_ON=hardhat` before testing. `FORK_MAINNET=true` with `MAINNET_RPC_URL` turns the hardhat network into a mainnet fork (`hardhat.config.ts:124-135`), used by `yarn test:mainnet-upgrade`.

Foundry: `foundry.toml` sets `src = "contracts"`, `test = "test/foundry"`, `fuzz.runs = 10000`, `fuzz.seed = 0x1234`. `forge-std` is a git submodule at `lib/forge-std` (`.gitmodules`); run `git submodule update --init` (or `yarn fuzz:setup`, interactive) before `forge`. Commands: `yarn fuzz` (`forge test --match-contract Fuzz -vv`), `yarn fuzz:fast` (1 000 runs), `yarn fuzz:deep` (100 000), `yarn fuzz:ci` (50 000), `yarn fuzz:coverage`; one test: `forge test --match-test testFuzz_ConversionRoundTrip_AssetsToShares`. The file `test/fuzz/EmberVaultConversions.t.sol` lies outside the configured test path and calls `initialize` with the owner and config arguments swapped (`:58` vs `contracts/EmberVault.sol:541-546`); do not use it as a model.

Echidna: `yarn fuzz:echidna` runs `echidna-test . --contract EmberVaultProperties --config echidna.yaml` (`testMode: assertion`, corpus `echidna-corpus`); `echidna.config.yaml` (`testMode: property`, corpus `test/echidna/corpus`) is what FUZZING.md documents and what the `echidna_*` boolean properties need. The harness constructor deploys nothing (`test/echidna/EmberVaultProperties.sol:22-25`), so every property dereferences an unset `vault`. Treat the property list as a specification, not a runnable suite.

CI (`.github/workflows/ci.yml`): `format-check`, `compile`, `test` (`yarn coverage`), and `validate-upgrades` as a matrix over mainnet, pharos, base, monad, arbitrum with `continue-on-error: true`. No job runs `forge` or `echidna`.

## Invariants and gotchas

- The rate rises when share value falls. Reason about `rate` as shares-per-asset, never as price-per-share.
- `totalAssets()` is modeled; `IERC20(asset()).balanceOf(vault)` is what pays. Operator sub-account withdrawals and fee accrual widen the gap without touching the rate.
- Charging fees after a burn under-collects; keep `_chargeAccruedPlatformFees()` before any `_mint`/`_burn`/rate change (`contracts/EmberVault.sol:1356-1361`).
- Admin setters are reachable only through `EmberProtocolConfig`; the vault-side modifier checks `caller`, so validation lives in the config and must be added there, not on the vault (`contracts/EmberProtocolConfig.sol:238-253`). Tests impersonate the config address to call setters directly.
- `setPausedStatus` on the vaults is guardian-only via the config and bypasses the timelock; `bridgeBurn` ignores the vault withdrawals pause but honors the protocol pause; `bridgeMint` and `_credit` ignore every pause and the blacklist by design so in-flight messages cannot revert (`contracts/EmberVault.sol:1086-1127`, `contracts/EmberVaultMintBurnOFTAdapter.sol:400-413`). See [./TIMELOCK.md](./TIMELOCK.md).
- `redeemShares` requires self-approval of the receipt token; `redeemShares(…, address(0))` is rejected up front because it would wedge the FIFO head (`contracts/EmberVault.sol:1188-1190`).
- A blacklisted request owner or receiver is skipped at processing and its shares returned; a blacklisted holder can still `transfer` shares, which is why the validator's missing-clock rule fires the time-based fee for any recipient without a deposit record.
- Sub-accounts can neither deposit nor receive shares (`contracts/EmberVault.sol:1839`, `:1872`); roles and sub-accounts are mutually exclusive and the config enforces it on every rotation.
- `setParkingLot(nonzero)` closes direct `deposit`/`mint` to everyone except the lot and explicitly allow-listed depositors (`contracts/EmberVault.sol:1821-1830`); an empty allow-list admits only the lot. The lot bypasses the validator allow-list (`:1846`).
- `EmberETHVault.initialize` probes the token with `IWETH.withdraw(0)` and a `symbol() == "WETH"` check (`contracts/EmberETHVault.sol:1970-1979`); `receive()` is unrestricted and stray ETH is not accounted (`:584`).
- `EmberVault` and `EmberETHVault` share an interface but not a fee implementation; a fix to `VaultPlatformFeeLib.charge` does not reach `EmberVault`, and vice versa.
- Linked libraries are not proxied: after changing a library, redeploy it and re-link by upgrading every implementation; proxies keep executing the old library until then. See [./AtomicLiquidity.md](./AtomicLiquidity.md).
- Hardhat's local network has `allowUnlimitedContractSize: true`; the suite will never fail on EIP-170. Run `yarn size` after touching `AtomicLiquidity`, `EmberETHVault`, or `EmberVault`.
- Custom errors shared by several contracts are declared once in `contracts/interfaces/IEmberProtocolConfig.sol:13-21`; redeclaring them inside a contract is deliberate where tests use `revertedWithCustomError` (`contracts/AtomicLiquidity.sol:26-39`), and selectors still match.
- Reserved for the off-chain indexer: every state change bumps `sequenceNumber` and emits `address(this)` as the first indexed field; library-emitted events redeclare the same signatures so DELEGATECALL emits them from the proxy. Changing an event signature breaks consumers that key on it.
